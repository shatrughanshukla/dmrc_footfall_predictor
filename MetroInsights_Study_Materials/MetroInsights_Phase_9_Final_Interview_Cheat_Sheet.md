## 5-minute project revision

MetroInsights is a Flask and scikit-learn prototype for station-level passenger-demand scenarios and service planning across a 226-station metro network. A user selects a station, date, time, and (for interchanges) line focus. The backend returns a demand estimate and day profile, date/service context, a schedule recommendation calculated from configured operations assumptions, and estimated network travel times.

The browser calls `/api/predict`. Flask validates date/time syntax, gets station and calendar context, runs the already-trained HistGradientBoostingRegressor using 23 features, calculates line-specific schedules, solves a shortest-path query, and serializes the result as JSON. Forecast/model metadata and compact tables load at startup. `pipeline/` scripts clean data, generate a synthetic training set, train/compare models, and save artifacts. The 130 MB synthetic CSV supports offline retraining; normal inference loads model/metadata instead of reading that CSV each request. Gunicorn starts the Flask app through `Procfile`.

The forecast's inputs include time/date cycles, station/line/typology identifiers, interchange indicators, and historical aggregates. Training compares station-mean and station-day-hour baselines, Ridge, and HistGradientBoostingRegressor using a chronological holdout beginning 2026-10-01. The holdout is still generated by the project's synthetic simulator; metrics are not accuracy against observed DMRC passenger counts.

Scheduling compares estimated hourly demand with configured comfortable boarding-clearance capacity, then returns practical frequency/headway recommendations subject to modeled policy, signaling, and fleet constraints. “Utilization” is not onboard crowding: the system does not model passengers already aboard, station alighting, or train-level occupancy. Travel times use a line-expanded graph and Dijkstra, with coordinate/average-speed edge costs, fallback segment weights, and interchange penalties. They are estimates, not live timetable routes.

The honest framing: this is an end-to-end planning prototype and scenario tool. Its value is the integrated workflow, explicit assumptions, model comparison, and network calculations. Before operational decisions, it needs observed ridership, verified timetables/capacity/topology, domain validation, security/input hardening, tests, and production monitoring.

## Project explanations

### 30 seconds

MetroInsights is a station-level metro demand and service-planning prototype. A user selects a station and scenario time; a Flask API combines a synthetic-data-trained demand model, configurable schedule calculations, calendar context, and Dijkstra-based network travel estimates. ### 2 minutes

The project helps explore how station demand varies by time and how that estimate relates to service recommendations. A browser sends station, date, time, and line-focus inputs to Flask. The API generates a 19-hour station profile from a fitted HistGradientBoostingRegressor, computes schedule recommendations from configurable capacity/headway/fleet assumptions, and returns shortest-path travel-time estimates from a line-expanded metro graph. The offline pipeline prepares station data, generates 104 weeks of synthetic scenarios, compares historical and ML baselines on a chronological holdout, and writes model and metadata artifacts. The web process loads these artifacts once and serves requests; it does not retrain from the 130 MB CSV per user request. Results are useful for demonstrating an integrated workflow, but the synthetic evaluation cannot prove DMRC accuracy. Utilization means estimated hourly demand relative to modeled boarding-clearance capacity, not people physically aboard. The next material step is observed data and expert-verified operating assumptions, followed by time-based validation and safe deployment controls.

## Core algorithms and concepts

- **Feature engineering:** cyclic sin/cos encodings for hour/day/month plus station, line, typology, calendar, and past aggregates.
- **Supervised regression:** HistGradientBoostingRegressor maps 23 feature values to a nonnegative hourly estimate; benchmark it against simple baselines.
- **Chronological holdout:** dates before 2026-10-01 train; later synthetic dates test. This better resembles forecasting forward but remains synthetic.
- **Scheduling arithmetic:** convert service constraints and demand/capacity assumptions into allowable frequency/headway and practical intervals.
- **Graph modeling:** node is `(station, line)`; edges are adjacent-station movement or paid interchange changes.
- **Dijkstra:** priority-queue shortest path for nonnegative weights; returns minimum estimated time, not a real timetable itinerary.
- **Request/response:** JSON API plus browser rendering; input validation and safe text rendering are important boundaries.

## Most important implementation details

- Inference uses 23 feature columns specified by saved metadata; deploy model and metadata together.
- Full-day profile covers hours 05:00 through 23:00; the modeled service window is 05:00 inclusive to 23:30 exclusive.
- Unknown station input is not allow-listed in the API and may fall through metadata defaults; reject with 400.
- JSON fields are assumed to have string types; validate types and lengths before `.strip()` or parsing.
- Frontend uses `innerHTML` with dynamic values in travel-table/no-results rendering; render untrusted strings with `textContent`/DOM construction.
- Joblib loading executes a trusted serialization format; never load user-supplied artifacts.
- `dashboard.js` request ID prevents stale responses replacing newer UI content; it does not cancel server-side work.
- `travel_graph` is built at startup; shortest-time searches repeat by origin and could be cached if profiling justifies it.
- Separate Gunicorn worker processes may each hold a model/data copy; tune workers against memory.
- Public endpoints have no app-level authentication or rate limiting in reviewed routes; upstream hosting controls may add boundaries.
- Synthetic holdout metrics, topology, capacity, headway, and interchange shares must not be presented as verified operational truth.

## Common interview traps

1. **“Real-time”** - Say “on-demand scenario calculation,” not live telemetry.
2. **Accuracy** - Synthetic holdout performance is not real-world DMRC accuracy.
3. **Capacity utilization** - Demand divided by modeled comfortable boarding capacity; not onboard occupancy.
4. **Travel time** - Graph estimate from assumed weights; not live route guidance.
5. **Dataset size** - Millions of synthetic rows do not mean millions of observed passenger records.
6. **“226 stations”** - Network coverage count, not proof every coordinate/topology is authoritative.
7. **Deploying CSV** - The large training CSV is for offline retraining; serving uses model and metadata artifacts.
8. **Scaling** - Measure latency/RSS/CPU before proposing Redis, queues, microservices, or Kubernetes.
9. **Security** - Describe unsafe sinks and preconditions; don't claim a demonstrated remote exploit without proof.
10. **Ownership** - Use only personal contributions and outcomes you can substantiate.

## Major limitations

- Training and holdout data are synthetic; no measured DMRC forecast validation.
- Operating capacity, headways, fleet parameters, topology and travel weights may be project assumptions or source data requiring verification.
- No train-level directional load balance, on-board passenger propagation, or boarding/alighting observations.
- Journey estimates omit actual timetables, waiting variability, walking/accessibility, disruptions, and live arrivals.
- Unknown station/wrong-type API inputs need robust validation; request-size/rate controls need deployment review.
- Dynamic frontend `innerHTML` is an unsafe rendering pattern where values are interpolated.
- No comprehensive tracked automated test suite or application monitoring was found in the reviewed repository.
- In-process state/artifacts and worker memory constrain how service behavior scales; no durable user scenario database is present.

## Top improvements, in order

1. Obtain observed passenger counts and verified topology/operations data; establish provenance and permissions.
2. Define target meaning and units precisely: station entries, boardings, train load, or another measure.
3. Build time-based evaluation, compare baselines, analyze errors by station/hour/holiday, and document limitations.
4. Validate request schema and station allow-list; bound request sizes; return safe errors.
5. Replace dynamic HTML interpolation with safe DOM/text APIs; protect model artifact supply chain.
6. Add regression tests for service boundaries, unknown/malformed inputs, artifact schema, schedule invariants, and route costs.
7. Measure response latency/RSS/cold starts; batch prediction or precompute route results only if profiling supports it.
8. Add readiness/structured logs/monitoring and a rollbackable code-model release process.
9. Add database, queue, shared cache, or separate model service only when durable product needs or measurements justify them.

## Top 50 difficult questions with concise answers

- **01. Q:** How would you prove this model is useful beyond synthetic data? **A:** Obtain governed observed counts, define the target, use temporal holdouts, compare baselines, stratify errors, and get domain review.
- **02. Q:** Why can a chronological split still overstate future performance? **A:** The synthetic generator may encode the same assumptions in train and holdout; shared simulator structure is not independent real-world evidence.
- **03. Q:** Could the training process leak a row’s target into its historical features? **A:** The current rolling aggregates subtract the current target and use prior dates; audit every future feature for prediction-time availability.
- **04. Q:** Why are per-row training history features different from live history metadata? **A:** They are constructed on separate paths; verify identical definitions, fallback behavior, and feature distributions to avoid train/serve skew.
- **05. Q:** Why not use random train/test splitting? **A:** Temporal dependencies can place near-identical dates in both sets and make future generalization look easier than it is.
- **06. Q:** What does R-squared fail to tell you here? **A:** It does not prove real-world validity, reveal station-specific failures, or describe absolute error and operational cost.
- **07. Q:** Why is MAPE problematic for low/zero footfall? **A:** Division by small actual values creates unstable or undefined percentage errors; complement it with MAE/RMSE and segmented analysis.
- **08. Q:** How do you detect drift once observed data exists? **A:** Track feature/target distributions and rolling time-based residuals by station, line, hour, and event; define retraining and escalation criteria.
- **09. Q:** How do you prevent future information in a calendar feature? **A:** Version the calendar source and include only information known at the selected forecast date; distinguish announced events from realized outcomes.
- **10. Q:** What if a station identifier appears during inference but was unseen in training? **A:** Use a deliberate unknown-category policy, report it, and validate coverage; do not silently map it to a real station index.
- **11. Q:** Why might an ordinal station index be a questionable model feature? **A:** The numeric order has no inherent distance meaning; tree splits may exploit arbitrary category ordering. Compare one-hot, categorical-aware, or embedding alternatives.
- **12. Q:** Would one global model or a station-specific model be better? **A:** Compare on temporal validation: a global model shares strength, while local models capture station patterns but need sufficient data and maintenance.
- **13. Q:** How should uncertainty be represented? **A:** Calibrate prediction intervals or quantiles on observed time-separated residuals; a point estimate alone hides uncertainty.
- **14. Q:** What does station-hour footfall mean operationally? **A:** Its precise definition must be fixed: entries, boardings, exits, or another count. The current synthetic target is not automatically onboard load.
- **15. Q:** Why can summed station demand double-count network riders? **A:** A rider may enter/exit at different stations or be counted under the synthetic target definition; network totals require a clear counting unit.
- **16. Q:** How would you calculate train onboard occupancy? **A:** Propagate directional passenger loads segment by segment using boardings, alightings, train assignments, and capacity, then validate measured loads.
- **17. Q:** Why is capacity utilization not a queueing model? **A:** It compares hourly demand with modeled hourly clearance capacity; it lacks arrival distributions, dwell time, queue state, and train-by-train loads.
- **18. Q:** What happens if demand exceeds the modeled fleet maximum? **A:** The optimizer should expose unmet demand/constraint status; verify calculations and never imply a feasible schedule if constraints bind.
- **19. Q:** How do you test a headway rounding invariant? **A:** Generate boundary cases and assert rounded values remain within signaling, policy, and fleet-derived frequency bounds.
- **20. Q:** Why could rounded headway violate a fleet constraint? **A:** Selecting the nearest practical headway after frequency clamping can alter frequency; recompute all constraints after rounding.
- **21. Q:** What does Dijkstra guarantee? **A:** A minimum summed path cost when edge weights are nonnegative; it does not guarantee that weights model reality.
- **22. Q:** Why use `(station, line)` rather than station-only graph nodes? **A:** It encodes platform/line state so line changes incur explicit interchange edges.
- **23. Q:** What breaks if interchange edges are missing? **A:** Routes that require transfers may become unreachable or incorrectly disconnected.
- **24. Q:** What breaks if topology says a false adjacency? **A:** Dijkstra can return a mathematically shortest but physically invalid route; topology source validation is essential.
- **25. Q:** How would you replace average-speed times with realistic journey times? **A:** Use verified segment running/dwell times, direction, service patterns, transfer walking/waiting and schedule/real-time data.
- **26. Q:** Would A* be faster than Dijkstra on this app? **A:** Possibly for large graphs with an admissible heuristic; at a few hundred stations, simpler Dijkstra may be adequate.
- **27. Q:** What is safe to cache in route calculations? **A:** Origin-to-destination results for a versioned immutable graph; invalidate on topology or weight changes.
- **28. Q:** What would you put in a forecast cache key? **A:** Canonical station, date, model/data/calendar versions, feature schema, and every input affecting the profile.
- **29. Q:** Why must an in-memory cache be bounded? **A:** Arbitrary station/date keys could grow process memory without limit.
- **30. Q:** Why is a per-worker cache not shared? **A:** Gunicorn workers are separate processes with separate heaps; sharing needs external storage or precomputed artifacts.
- **31. Q:** How would you avoid train/serve skew? **A:** Use one tested feature builder for training/inference where possible and validate schema/value parity with fixed fixtures.
